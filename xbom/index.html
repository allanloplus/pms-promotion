WHY

為什麼需要

Allan 顧問

稽核時我常問：「Log4Shell 那種事件再發生，你們多久能回答『我們有沒有用到』？」多數單位要幾天到幾週。阿拉蕾，你怎麼看？

阿拉蕾

因為沒有一份可以查詢的組成清單。資產清冊通常只記到「某某系統一套」，裡面有什麼沒人說得清楚。BOM（物料清單）就是把資產清冊往下再展開一層。

Allan 顧問

那有 SBOM 不就夠了？

阿拉蕾

不夠。SBOM 只列程式庫，但風險不只在程式庫。下面這四種情況，SBOM 都看不到。

  • 程式庫都沒問題，但基底映像檔三個月沒更新。
  • 程式庫都沒問題，但驗證碼用了已不安全的雜湊演算法。
  • 程式庫都沒問題，但個人資料經由某個沒人記得的第三方服務送出境外。
  • 掃出 40 個弱點，其中 38 個其實不影響我們，但沒人留下判定紀錄，每次稽核都要重新解釋。
人工清冊XBOM
產生方式人填工具自建置過程產生，人只補工具看不到的部分
更新時機年度盤點每次程式變更
比對弱點無法自動新弱點公布當天即可得知是否受影響
驗證正確性抽樣訪談重新產生一次，比對是否相同
交換各家格式不同國際標準格式（CycloneDX 為 ECMA-424，SPDX 為 ISO/IEC 5962）
TYPES

X 代表哪些清單

Allan 顧問

所以 XBOM 的 X 是什麼意思？

阿拉蕾

eXtended，也可以讀成「任何一種」。用同一種清單思維，把每個問題各做成一份清單。前六種是盤點，VDR 與 VEX 是評估與處理，CDXA 是聲明。

Allan 顧問

這跟 ISMS 的資產盤點、風險評鑑、適用性聲明是同一個順序，只是對象縮小到單一系統，格式改成機器可讀。不適用的清單呢？

阿拉蕾

一樣要寫下理由。這張適用性表就像 ISMS 的適用性聲明，本身是可稽核的紀錄。

清單它回答的問題對應的 ISMS 概念本案

LIMITS

能證明什麼、不能證明什麼

Allan 顧問

客戶一定會問：做了 XBOM，能證明系統是安全的嗎？

阿拉蕾

不能。它能讓安全的說法變得可以查證，這是兩件事。

Allan 顧問

這點一定要先講清楚。ISMS 也不是保證不出事，而是證明風險被識別、被處理、被持續監控。另外，拿到一份清單，我會先問它是哪一類。

阿拉蕾

我這次產生的 SBOM 與 CBOM 屬於 Source 類，依據是原始碼與鎖定檔。拿它主張「上線環境就是這樣」，中間還缺一段證據，我在清單裡有標明。

能提供的保證

  • 清單涵蓋正式環境全部軟體元件，由工具自動產生，可重新產生比對
  • 元件未被竄改，每個元件附完整性雜湊
  • 截至某時點，這些元件沒有未處理的已知弱點
  • 每個弱點都經過判定，載明理由、判定人與複核期限
  • 密碼學與資料流向已被識別，並附原始碼位置
  • 清單沒有過期，每次變更重新驗證

不能證明

  • 沒有未知弱點。清單只能比對已公開的弱點
  • 自己寫的程式沒有漏洞。這要靠程式碼審查與安全測試
  • 實際上線的就是清單所描述的。除非從上線環境採集，或以簽章綁定
  • 組態正確、營運安全。權限、備份可否還原、人員是否依程序，都在清單之外

正確的說法：「我們知道系統由什麼組成，持續檢查這些組成有沒有已知問題，每個問題都有處理決定，而且這些說法都有您可以自行查證的證據。還不知道的部分，我們也列出來了。」

先問：這份清單是哪一類

同樣叫 SBOM，可信度可以差很多。美國 CISA 依產生時機分為六類，愈後面愈接近真實。拿 Source 類清單主張「上線環境就是這樣」，中間還缺一段證據。

類型依據代表本案

Source原始碼與鎖定檔宣告要用什麼SBOM、CBOM 屬此類
Build建置過程實際建進去什麼CI 映像檔清單，已定義待啟用

METHOD

八個步驟

Allan 顧問

從哪裡開始？直接跑掃描工具嗎？

阿拉蕾

不是。前三步是思考，不需要工具。我先讀部署檔把範圍畫出來，再決定哪些清單適用，然後分辨哪些資訊工具看得到、哪些只有人知道。

Allan 顧問

第三步是關鍵。工具看不到的那些，才是稽核真正想看的：有人想過這個金鑰放哪裡、這個服務拿到什麼資料。

阿拉蕾

所以這部分我寫成宣告檔，放進版控跟程式一起審查，再用自動檢查把它綁在程式上，避免過期。

  1. 界定範圍使用者接觸什麼、跑在什麼上面、由什麼組成、需要哪些外部服務。範圍是讀部署檔讀出來的，不是掃出來的。
  2. 決定適用哪些清單逐一判定，不適用者寫下理由。
  3. 分辨機器與人哪些資訊工具看得到，哪些只有人知道。這決定清單的維護方式。
  4. 自動盤點以通用工具自鎖定檔與部署定義檔產生，不重造輪子。
  5. 人工宣告把架構知識寫成宣告檔，納入版控與審查。
  6. 比對弱點並判定從「有什麼」推進到「有沒有問題、怎麼處理」。
  7. 驗證與自動化結構、雜湊、參照、漂移。納入 CI，每週重新比對。
  8. 對照要求、列出缺口把清單轉為符合性證據與改善計畫。

步驟 3 是 XBOM 與單純 SBOM 最大的差異

CASE

本案盤點結果

Allan 顧問

盤點出來的結果如何？

阿拉蕾

設定檔裡只寫了 3 個套件，實際帶進 67 個，間接相依占 96%。104 個套件比對弱點資料庫，命中 0 筆。

只看設定檔的人會以為系統只用了 3 個套件。那套件以外呢？

這才是重點。資料庫與密碼學實作都內建在執行環境裡，不是套件，掃描工具不會列出。我依層次整理成下面這張圖，橘色那層是這次盤點最不完整的。

DESIGN

四個關鍵設計

Allan 顧問

清單不難產生。我關心的是：憑什麼相信它？先說那個「0 筆弱點」。

阿拉蕾

我也會懷疑。所以每次比對前，先查一個已知有弱點的套件當對照組，查不到就中止並宣告結果不可信。下面四個機制各回答一個這類問題，而且每個我都故意破壞過一次，確認它真的會擋。

Allan 顧問

通過的檢查如果從沒失敗過，我不會當它有效。這個作法可以直接寫進查檢表。

一、「零發現」可信嗎：正向對照

看到 0 個弱點應該先懷疑：是真的沒有，還是掃描器壞了、連不上資料庫？每次比對前先查一個已知有弱點的套件。查不到就中止並宣告本次結果不可信。

弱點比對 104 個元件：命中 0 筆，待處理 0 筆（正向對照命中 5 筆）

"x:vdr:canary":   "pkg:npm/lodash@4.17.15 → 命中 5 筆（掃描管道有效）"
"x:vdr:coverage": "npm 套件；不含 Node.js 執行環境、容器作業系統套件與主機"

二、宣告會不會過期：未宣告的密碼學用法使產生器中止

每項密碼學資產的宣告附有原始碼比對規則。程式中出現密碼學呼叫卻沒有對應宣告，或宣告了但程式中已找不到，都會中止。測試時暫時加入一行 MD5：

[XBOM 產生失敗] 原始碼中有未宣告的密碼學用法，請於 declared/crypto.json 補上對應資產：
  src/util.js:28  const weak = (s) => require('crypto').createHash('md5').update(s)…

三、清單是現在的嗎：重新產生再比對

序號由內容雜湊導出，版本以原始檔內容雜湊識別。同一份程式碼必定產生相同清單，因此驗證器可以重新產生一次再比對。測試時在原始檔加一行註解：

✗ 失敗  清單與目前程式碼一致（無漂移）
驗證未通過：1 項失敗（共 16 項）

四、弱點有沒有被處理：未判定者擋關，判定會到期

命中不等於受影響，必須有人判定並留下理由。本案實際命中為 0，因此暫時加入有弱點的套件模擬流程，結束後還原。

弱點比對 105 個元件：命中 5 筆，待處理 5 筆        ← 關卡失敗，結束碼 2
  ! GHSA-35jh-r3h4-6jhm high Command Injection in lodash
  …

// 登錄判定後重新產生，待處理降為 4 筆
"GHSA-35jh-r3h4-6jhm": {
  "state": "not_affected",
  "justification": "code_not_reachable",
  "detail": "（教學示範）受影響函式為 _.template；本工具未呼叫該函式",
  "decidedBy": "示範人員", "decidedAt": "2026-11-25", "reviewBy": "2027-02-25" }
  • 「不受影響」必須選定理由類別，不能只寫「評估後無風險」。無法確定時一律視為受影響。
  • 判定有複核期限，逾期自動退回「判定中」。今天呼叫不到的函式，明年可能就用上了。
  • 弱點報告獨立成檔。程式沒改，明天也可能多出一個弱點，兩者更新節奏不同。
PITFALLS

實作中踩到的三個坑

Allan 顧問

過程中有沒有出錯？

阿拉蕾

有三次。最值得講的是第二次：我的反向測試第一次就通過了，後來才發現測試用的那行程式剛好掩蓋了偵測規則的漏洞。

Allan 顧問

做不到的部分呢？

阿拉蕾

我沒辦法建置映像檔、沒有正式主機的存取權，也不能代替主管簽署。這些都寫在清單裡，沒有略過。

Allan 顧問

只呈現通過項目的報告，我反而會打低分。知道自己不知道什麼，是成熟度的指標。

發生什麼原因教訓
工具回報 cannot validate BOM，沒有其他說明結構驗證需另外安裝選用套件「無法驗證」不等於「驗證通過」。若當時直接關掉驗證，之後所有清單都不會被檢查
反向測試第一次通過，其實偵測規則有漏洞測試用的那一行剛好同時含有兩種寫法，掩蓋了其中一種抓不到的事實反向測試要用最小的案例，一次只測一件事
清單提交後立刻與現況不符，重新產生再提交又不符以 Git 提交代碼識別版本，而提交清單本身會改變代碼以原始檔內容雜湊識別。清單本質上是建置的產出物，正式作法是隨發行版產生並保存

本次未完成，如實記錄

  • 實作環境無法建置映像檔，容器層的盤點改於 CI 進行。尚未涵蓋的範圍在清單中以 aggregate: unknown 標示。
  • 執行環境與 TLS 參數係依部署定義檔與元件預設值宣告，不是上線環境實測，清單中以屬性標明。
  • 清單未簽章；符合性聲明的簽署欄位留空，那必須由組織的權責人員簽署。
FINDINGS

每份清單各自揭露了什麼

Allan 顧問

AUDIT

稽核員如何查核 XBOM

阿拉蕾

如果你是來稽核我的，會怎麼查？

Allan 顧問

四個面向：有沒有漏、寫的對不對、是不是現在的、有沒有被用來管理。前兩個一個由實況反查清單，一個由清單反查實況。以這個案例，15 分鐘可以抽完一輪。

面向稽核問題查核方法
完整性清單有沒有漏？由部署檔反向抽查：選一個映像檔、一個外部連線、一處密碼學呼叫，看清單裡有沒有
正確性清單寫的是對的嗎？由清單正向抽查：選一個元件核對版本與雜湊；選一項密碼學資產，依所附行號打開原始碼
時效性清單是現在的嗎？要求當場重新產生並比對；查看最近一次弱點比對時間
有效性清單有被用來管理嗎？查判定紀錄是否有理由與複核；查 CI 執行歷史是否持續；查關卡是否曾擋下變更

常見的不符合情形

  • 有 SBOM 但為一年前產生，之後相依已多次變更。
  • 只列直接相依，未含間接相依。
  • 弱點命中項目無判定紀錄，或一律標為「不受影響」而無理由。
  • 掃描工具回報 0 弱點，但無法證明工具有效。
  • 清單含金鑰、密碼等機密資訊並對外提供。
  • 宣稱有 CBOM，但只列演算法名稱，無用途、金鑰位置與保護方式。
  • 供應商交付之軟體未附清單，合約亦未要求。

15 分鐘抽樣示範

  1. 正向：在摘要中選「HMAC-SHA256 → src/auth.js:11」，打開該行確認。
  2. 反向：在部署檔找到 一個映像檔，於 OBOM 中確認存在且版本標示與實際相符。
  3. 時效：要求受稽方執行驗證指令，觀察「無漂移」是否通過。
  4. 有效：開啟弱點報告，確認比對時間、對照測試結果與涵蓋範圍聲明。
  5. 誠實度：確認受稽方有一份「未涵蓋或未保證」清單，清楚自己不知道什麼。
