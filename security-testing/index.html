安全檢測對話教學

做完 XBOM 之後，下一步是什麼？一位顧問和一個 AI 小助理，替同一套上線系統做了一輪安全檢測：源碼檢測、機密掃描、存取控制測試、注入檢查與程式碼審查。讀完這段對話，你會知道各種檢測各自證明什麼、怎麼規劃、怎樣的報告才能當證據，最後怎麼產出一份第一方自行檢測報告。

CONCEPT

先釐清一個觀念

Allan 顧問

做完 XBOM，我的理解是：它就是把 AI 生成的程式拆解成元件，並識別其中的風險。對嗎？

阿拉蕾

一半對。XBOM 跟程式是不是 AI 生成的無關，人寫的系統一樣能做。更重要的是：它拆解的是「用了什麼」，不是「寫了什麼」。

Allan 顧問

所以自己寫的那幾千行程式，XBOM 其實沒檢查？

阿拉蕾

對。對一套 AI 生成的系統，XBOM 沒檢查到的部分，恰好就是 AI 寫的那部分。這就是下一步要補的。

XBOM 涵蓋XBOM 不涵蓋
對象別人寫的元件、執行環境、密碼學機制、外部服務自己寫的程式
識別的風險元件的已知弱點、盤點時浮現的治理缺口程式邏輯錯誤、權限控管漏洞、未知弱點
本案結果104 個元件，已知弱點 0自寫程式中 17 項發現

兩個結果都是真的。它們回答的是不同的問題。

METHODS

各種檢測各自證明什麼

Allan 顧問

那我熟悉的源碼檢測和弱掃，做了就夠嗎？

阿拉蕾

每一種檢測只回答一個問題，也各有看不到的地方。沒有任何單一檢測能證明系統安全，要把它們疊起來。

Allan 顧問

稽核時我最常看到的錯誤，就是拿未登入的弱掃報告來主張存取控制有效。那份報告根本沒測到。

檢測回答的問題抓得到抓不到

源碼檢測自己寫的程式有危險寫法嗎？注入、不安全的函式、寫死的密碼權限邏輯、業務邏輯
機密掃描版本庫裡有沒有放進金鑰？歷史提交中的機密機密的使用是否妥當
映像檔掃描執行環境有弱點嗎？作業系統套件弱點應用程式本身
弱點掃描從外面看得到已知問題嗎？過期服務、TLS、常見網頁弱點登入後才看得到的問題
存取控制測試不該有權限的人進得去嗎？越權、跨租戶存取取決於測試設計

RESULT

同一套程式、同一天，各方法找到什麼

實際跑下來，哪一種找到最多？

自動化工具在自寫程式裡沒有找到任何真實問題，回報的 10 筆全是誤判。真實問題都來自專門設計的測試與人工式審查。

PATTERN

AI 生成的程式有什麼不同

Allan 顧問

所以 AI 寫的程式比較不安全嗎？

阿拉蕾

這個案例看到的是：寫法層面做得好，規則一致性層面有缺口。多數發現是同一種型態，某條規則在一個地方做了，在另一個地方沒有。

Allan 顧問

這人寫的程式也常見。

阿拉蕾

對，不是 AI 獨有。但 AI 產出的速度遠快於人審查的速度，這種不一致容易累積。對策是把規則寫成會自動執行的測試，讓機器檢查一致性。

規則做到的地方漏掉的地方
資料依租戶隔離全部業務物件某個系統層級的查詢
系統設定限特定帳號類別讀取修改
實施者不得自行驗證驗證當下的檢查事後改派負責人
依來源限制嘗試次數標準寫法的網址大小寫或斜線不同的網址
輸出一律跳脫使用者輸入的資料管理員可編輯的設定名稱

每一條規則在說明文件中都寫得很清楚，程式的每一處單看也合理。問題在於沒有人確認規則在每一個該適用的地方都適用了。

PLAN

如何規劃

Allan 顧問

那要怎麼排順序？直接找廠商做滲透測試嗎？

阿拉蕾

先自己做。不要花錢請人告訴你工具五分鐘就能找到的東西。自行檢測並修補之後，第三方的時間才會用在只有人才找得到的問題上。

Allan 顧問

還有一件事要先做：決定受測版本。報告如果對應不到上線的版本，就沒有證明力。

  1. 備妥受測版本、獨立測試環境、各角色與至少兩個租戶的測試帳號、威脅模型。
  2. 自行檢測源碼檢測、機密掃描、存取控制矩陣、注入檢查、程式碼審查。修補並寫成回歸測試。
  3. 第三方弱點掃描與滲透測試。修補後一定要複測。
  4. 整理證據報告與 XBOM 綁在同一版；更新符合性主張；寫下限制。

威脅模型決定測什麼

資產主要威脅推導出的檢測重點
各租戶的業務資料別的租戶的使用者越權讀取全部路由的跨租戶存取測試
核准與驗證紀錄的可信度當事人自行核准、事後竄改職務區隔與核准完整性的邏輯測試

攻擊者清單一定要包含有合法帳號的人。別的租戶的使用者、專案內部想讓自己項目過關的人，一般掃描工具都把他們當成正常使用者。

MATRIX

存取控制矩陣

Allan 顧問

存取控制為什麼不能用現成工具測？

阿拉蕾

通用工具不知道「甲公司的稽核員不該看到乙公司的紀錄」。這條規則只存在於系統的設計裡，所以要自己寫成測試。

Allan 顧問

82 條路由，逐條人工檢查很難不漏。

阿拉蕾

所以讓機器逐條打一遍。測試直接讀原始碼列出全部路由，填入目標租戶的真實物件編號，用每一種不該有權限的身分去呼叫。任何非預期的成功就是越權。

三個設計重點

  • 路由清單取自原始碼。新增路由若無法歸類，測試會失敗，強迫開發者決定它該受什麼保護。
  • 用真實物件的編號。只測不存在的編號，會把「權限正確」與「物件不存在」混為一談。
  • 嚴格要求拒絕。若回的是輸入驗證錯誤，代表驗證先於授權，換一組合法輸入就可能成功，不能算通過。

結果：80 條路由對全部無權身分正確拒絕，另外找到 1 處真實的跨租戶外洩。業務物件的端點全部正確，出問題的是不屬於任何業務物件的系統層級端點。這是多租戶系統最常見的漏洞位置。

LESSONS

實作中的四個教訓

Allan 顧問

過程中最值得記下來的是什麼？

阿拉蕾

有兩次是我自己的檢測或修補不完整，被另一種方法或測試抓到。

Allan 顧問

這種紀錄我最想看。

一、工具的輸出是候選，不是發現

源碼檢測回報 23 筆。逐筆打開程式判定後，13 筆真實、10 筆誤判。直接把 23 寫進報告，或為了數字好看而關掉規則，都是錯的。每筆判定留下理由與複核期限，未判定的使關卡失敗。

源碼檢測：10 筆結果（8 筆相異）；已判定為誤判或可接受 8 筆；待處理 0 筆；判定逾期 0 筆

"state": "false_positive",
"detail": "檔名來自白名單函式，僅接受四個語言代碼，無法帶入路徑字元…",
"decidedBy": "AI 助理初判，待系統負責人複核", "reviewBy": "2026-12-25"

二、每個測試都要看它失敗一次

修補完成後，暫時還原修補、只保留測試再跑一次。全部失敗，才能確定測試真的抓得到問題。省略這一步，就分不出「修好了」與「根本沒測到」。

not ok 職務區隔：實施者不得驗證自己實施的項目，改派負責人亦無法規避
not ok 風險接受：核准後若內容或風險值變更，原核准失效
not ok 流量限制：以不同大小寫或結尾斜線的網址無法取得額外額度
…
# pass 15　# fail 8

三、修補不完整，被測試抓到

流量限制原本依請求路徑計數，換個大小寫就有新額度。第一版修補處理了兩種寫法，但第三種仍然繞過。因為回歸測試涵蓋了多種變化，這個不完整的修補沒有過關。

{{ 標準: 429, 大寫: 429, 結尾斜線: 429, 整段混合大小寫: 400 }}   ← 仍可繞過

四、「未發現」只對檢查過的範圍成立

注入檢查把探針寫進 1,818 個資料欄位，開了 368 個畫面，回報未發現。同時進行的審查卻找到一整類問題。原因是探針略過了設定表，而輸出並不會提醒這件事。補上之後，檢查反過來找到審查漏掉的 3 處。

人工式審查與自動檢查互相補盲。只做其中一種都不完整。

AUDIT

稽核員如何查核安全檢測

阿拉蕾

如果你來稽核我這次的檢測，會怎麼查？

Allan 顧問

還是那四個面向，問法不同。我最想看的是你把修補還原，讓我看測試失敗。

面向稽核問題查核方法
完整性該測的都測了嗎？對照威脅模型與驗證基準，找出沒有對應檢測的項目
正確性檢測方法有效嗎？要求展示測試在未修補時會失敗；抽查誤判的判定理由
時效性受測的是現在上線的版本嗎？核對報告的版本識別與上線版本；查 CI 最近執行時間
有效性發現有被處理嗎？抽查修補與複測；查未結發現是否有決定與期限

常見的不符合情形

  • 弱掃報告只做未登入掃描，卻用來主張存取控制有效。
  • 報告只列發現，沒有列測試項目。
  • 報告的受測版本對應不到上線版本。
  • 發現已修補但沒有複測紀錄。
  • 工具回報的項目被整批標為誤判，沒有逐項理由。
  • 為了通過關卡而關閉規則或跳過測試。
  • 測試者就是開發者，卻以此作為獨立驗證的證據。
  • 修補後未檢查同類問題是否存在於其他位置。

Allan 顧問

對內足夠開始，對外不足以當證明。我參與了這套系統的工作，我出的報告沒有獨立性。

阿拉蕾

對。那是滲透測試的專長。自行檢測的價值，是讓第三方的時間用在只有他們能做的事情上。

優先委外項目理由
1滲透測試（提供各角色帳號）風險集中在存取控制與業務邏輯，只有人能測
2經實際部署環境的弱點掃描補上自行檢測沒有實測的通訊層與主機層
3ASVS 第二級逐條驗證若需對外主張符合特定等級
4第三方源碼檢測若客戶或法規指定工具或資格
  • 把自行檢測的結果交給廠商。廠商不必重新發現已知問題，可以直接驗證修補是否完整，把時間用在更深的地方。
  • 評選時看報告範例。有沒有列測試項目、發現能不能重現、有沒有業務邏輯類的發現。
  • 把廠商的每一項發現寫成回歸測試。報告是一次性的，回歸測試是持續的。

做過自行檢測的組織，才有能力判斷第三方報告的品質。拿到報告之後怎麼讀，見本系列第三篇：解讀第三方檢測報告。

REPORT

FOLLOW-UP

修補上線之後：把掛著的掃描收掉

Allan 顧問

修補部署了、報告也出了。可是報告的「後續事項」還掛著三項：兩種排進自動流程的掃描沒人看過結果，還有一項設定待實測。這算做完了嗎？

阿拉蕾

不算。工具跑完不等於檢測做完。而且收這三項的過程，我自己就判斷錯了兩次。

Allan 顧問

兩次？說來聽聽。

阿拉蕾

第一次：要確認應用程式的埠從外部連不到。我從自己的環境測，連線失敗，看起來是好消息。但我的環境連任何主機的非標準埠都會失敗，這個結果什麼都證明不了。

Allan 顧問

所以後來是我在自己電腦上測的。結果有兩行：主機有回應、那個埠連不上。

阿拉蕾

兩行要一起看。第一行是對照組，證明到得了那台主機，第二行的「連不上」才有意義。得到否定的結果時先問：如果答案相反，這個測試看得出來嗎？

Allan 顧問

第二次呢？

阿拉蕾

映像檔掃描第一次顯示總筆數時，我說這個數量在這類映像檔很常見。然後嚴重度分布出來，裡面有重大等級的。那句話說早了。

Allan 顧問

可是元件清單的弱點比對一直是零。怎麼會差這麼多？

阿拉蕾

兩個數字都對，範圍不同。清單比對看的是應用程式宣告的相依套件；映像檔掃描看的是整個容器，包含作業系統，以及基底映像檔附帶的一切。這就是當初清單報告裡寫的「執行環境層未掃描」那個缺口。

Allan 顧問

幾百筆要怎麼看？逐筆看不完。

阿拉蕾

先不看嚴重度。先依「來源」和「有沒有修補版本」分組。一分就變成兩個問題，各有各的處理方式。

來源有修補版本嗎判斷處置
基底映像檔附帶的建置工具全部有不在應用程式的相依清單裡；系統執行時根本不呼叫它移除，而不是升級
作業系統套件全部沒有上游對評為次要的問題不另發更新以弱點為單位逐一判定並留下理由
Allan 顧問

能修的那一半，處置是「刪掉」？

阿拉蕾

對。建置完成後那套工具再也用不到。移除之後，映像檔裡同類套件的數量正好等於元件清單上的數量。清單和實物對起來了。

Allan 顧問

動了映像檔，原本的測試測得到嗎？

阿拉蕾

測不到，原本的測試跑的是原始碼。所以自動流程加了一步：用剛建好的映像檔實際啟動系統，確認有回應。改了交付物，就要測交付物本身。

Allan 顧問

不能修的那一半，裡面有「重大」。你判定不受影響，我要怎麼相信？

阿拉蕾

每一個弱點查三件事：版本真的在受影響範圍嗎？應用程式會執行到那個套件嗎？會載入的話，觸發條件成立嗎？理由寫到第三人可以重查的程度。

Allan 顧問

「重大」是怎麼回事？

阿拉蕾

通用評分回答的是「這個弱點最壞能多嚴重」，它假設存在一個會把攻擊者的輸入交給那個函式的程式。「在我的系統裡有多嚴重」只能自己判定。這正是 VEX 存在的理由。

Allan 顧問

但判定的人是你，一個 AI。

阿拉蕾

所以紀錄上寫的是「初判，待負責人複核」，複核期限只給一個月，到期沒人複核，自動流程就失敗。把握度比較低的那一筆，紀錄裡也明說了。

判定紀錄要有的內容為什麼
理由類別與具體說明「評估後無影響」不是理由
判定所依賴的部署前提部署方式改了，判定要重做
判定人，以及是初判還是已確認AI 或工具的初判不能當成人的確認
複核期限，逾期即擋關判定會過期：新的利用方式、新的用法
沒有查證的部分讓複核的人知道從哪裡看起

判定為不受影響，不代表問題消失：那些套件還在，日後有新弱點要再判定一次。治本的作法是換用不含這些套件的基底映像檔，代價是容器內沒有任何除錯工具。這是架構層級的取捨。本案評估後決定暫不更換：會消失的正是判定時最有把握的那一半，執行環境本身需要的函式庫換了也還在，而更換對正式環境有風險。決定連同理由與重新評估的條件一併留下紀錄。「不做」也是一項決定。

依本頁的公開原則，這一節只寫類型與教訓，不列數量、套件名稱與弱點編號；內容於修補部署至正式環境後才加入。

EDGE

再往外一層：代理、主機，和一項查錯原因的警告

Allan 顧問

應用程式的映像檔處理完了。但對外的第一線不是應用程式，是前面那台反向代理。它掃了嗎？

阿拉蕾

還沒。主機的作業系統也沒有。另外網頁掃描還有一項警告，我以為修好了，其實沒有。

Allan 顧問

先說那項警告。怎麼會以為修好了？

阿拉蕾

警告只有一行名稱，大意是安全政策有指令沒設定。我猜是某個來源設得太寬，就把它收緊了。重新掃描，警告還在。

Allan 顧問

沒看明細就動手。

阿拉蕾

對。所以反過來做：先讓流程把每項警告的明細印出來。一印才知道，同一個編號底下是兩件不同的事，而且沒有一件是我猜的那個。

警告出現在哪裡真正的原因處置
有指令未設定不存在的網址找不到的路徑由框架自己回覆，它用自帶的精簡政策蓋掉了系統設定的那一份改由系統回覆，並加測試
允許行內樣式首頁前端有許多行內樣式評估後接受：樣式不能執行程式，腳本一直嚴格限制
Allan 顧問

第一項有意思。政策明明設了，首頁的測試也過了。

阿拉蕾

因為錯誤頁面走的是另一條路。設定寫了、測試也有，但測的是首頁。安全設定要測每一種回應：錯誤頁面、轉址、靜態檔案常常各走各的。

Allan 顧問

新加的測試有先看它失敗嗎？

阿拉蕾

有。修正前失敗，修正後通過。

Allan 顧問

回到反向代理。掃出來怎麼樣？

阿拉蕾

重大與高風險有十幾個，分兩類。一類在映像檔的作業系統套件，主要是加密函式庫；一類在代理程式自己的執行檔裡。

Allan 顧問

加密函式庫的弱點，在一台負責加密連線的代理上。聽起來很嚴重。

阿拉蕾

我的第一反應是：這個代理用的語言自帶加密實作，應該不會用到系統的函式庫。但「應該」不是證據。所以在流程裡加了一步，直接檢查那個執行檔有沒有載入系統函式庫。

Allan 顧問

結果？

阿拉蕾

靜態連結，一個系統函式庫都沒載入。而且這一步每次掃描都會執行，哪天上游改了建置方式，判定的依據不成立時會直接看到。

Allan 顧問

等等。那幾筆裡有新一代傳輸協定的弱點，而主機確實開著那個協定用的埠。

阿拉蕾

這正是容易誤判的地方。只看「有沒有開這個功能」會判成受影響。要看的是「這個功能由誰實作」：開著的功能是代理程式內建的，不是那個函式庫提供的。

Allan 顧問

第二類呢？在執行檔裡面的。

阿拉蕾

映像檔掃描只知道「用了這個版本的模組」。語言官方的工具可以進一步檢視執行檔，列出實際含有的受影響函式。

Allan 顧問

含有就會被呼叫嗎？

阿拉蕾

不會。這個代理把全部功能編在同一個執行檔裡，用不用取決於設定檔。所以最後還要對照設定檔：我們只用了轉送、壓縮、加標頭三項。

證據的層次能回答什麼不能回答什麼
映像檔掃描用了哪個版本的元件那段程式有沒有被編進去
檢視執行檔受影響的函式在不在執行檔裡會不會被呼叫
對照設定檔哪些功能有啟用設定以外的內部呼叫
讀原始碼確切的呼叫路徑本案沒有做，判定紀錄裡明說了
Allan 顧問

這一輪你還有哪裡差點出錯？

阿拉蕾

有一筆在壓縮模組，而設定檔正好啟用了那種壓縮。我本來要建議把它關掉。把公告讀完才發現弱點在解壓縮，而代理只壓縮回應，從不解壓縮用戶端送來的資料。

Allan 顧問

差點為了一個到不了的路徑去改正式環境。

阿拉蕾

公告要讀到「哪個方向、哪個函式」才判定。全部判定之後交給您確認，其中一筆中等風險的不在關卡範圍，但因為它在對外服務的路徑上，另外記成關注事項。

Allan 顧問

主機呢？它不在儲存庫裡，自動流程碰不到。

阿拉蕾

所以請您在主機上執行一段只讀取資訊的指令，把輸出交回來判讀：系統是否還在支援期、有沒有更新後沒重開機、自動更新是否真的在跑、對外開了哪些埠、遠端管理怎麼登入。

Allan 顧問

結果大致正常，改了兩件事：關掉密碼登入，以及把自動更新不涵蓋的那類更新排進每月例行。

阿拉蕾

這次檢查也順便印證了先前的結論：應用程式的埠在主機上根本沒有對外聆聽。

Allan 顧問

還看到一件範圍以外的事：同一台主機上有另一個系統，共用同一個代理。

阿拉蕾

它不在這一輪任何檢測裡。但它若被攻破，攻擊者就在同一台主機上。這寫進了報告的限制。盤點範圍時，共用基礎設施的鄰居要列出來。

主機檢查只做了一次。它回答「今天的狀態」，不回答「下個月還是不是這樣」。代理程式的三筆弱點上游已有修補，但含修補的映像檔還沒發行，目前只能等；判定也依賴現行的設定檔，設定一改就要重做。這些都如實寫在紀錄裡。

TIPS

給下一位實作者的提醒

Allan 顧問

最後一樣留幾個提醒。

  1. 工具的輸出是候選，不是發現。每一筆都要打開程式看。
  2. 誤判要留下理由與複核期限，不要關掉規則。
  3. 存取控制要自己寫測試，用真實物件的編號、多種身分。
  4. 每個測試都要看它在未修補時失敗一次。
  5. 同一類問題要測多種變化，否則不完整的修補會過關。
  6. 「未發現」只對檢查過的範圍成立，輸出要寫明檢查了什麼。
  7. 至少用兩種方法交叉檢查，它們的盲點不同。
  8. 修補也是變更，要重新產生清單、重跑全部測試。
  9. 做完檢測不等於有報告。專門留時間寫，封面就寫明是自行檢測。
  10. 去識別化要同時做到「認不出」與「打不了」，而且修補部署後才公開。
  11. 否定的結果要有對照組；排進自動流程的掃描要有人看結果。
  12. 用不到的元件，移除優於修補；改了交付物就要測交付物本身。
  13. 沒看到明細就修，修到的可能是別的問題。安全設定要測每一種回應。
  14. 「應該不會用到」要換成一次量測；弱點公告要讀到哪個方向、哪個函式。
